# 02i. Этап 2a-2 — граф связей, зависимости, составные узлы на карте

Цель: связи между сервисами и устройствами — часть модели Hestia. Пользователь тянет связь на карте от
порта сервиса к другому сервису или к устройству, Hestia строит план (обе стороны), после
подтверждения применяет и следит за состоянием. При создании экземпляра обязательные зависимости
(`requires`) закрываются существующими экземплярами или новыми — одним планом. Сервер на карте —
составной узел: внутри экземпляры плагинов и их контейнеры, порты `provides` — ручки на границе.

Основа — 04-ecosystem.md, каркас — 02h (включая «Отклонения»). Первый реальный потребитель — HestiaCA
(2a-3); в этом этапе модель проверяется демо-плагинами `hestia-hello` и новым `hestia-probe`.

## Решения (2026-11-19, с пользователем)

- Два вида связи:
  - **сервис ↔ сервис**: потребитель (`requires T`) ← поставщик (`provides T`). Hestia просит
    поставщика выдать доступ (данные по контракту типа T, секреты — через секреты Hestia), передаёт их
    потребителю, тот подключается;
  - **сервис → устройство**: поставщик сам настраивает клиентскую сторону на выбранном устройстве
    (mount, доверие к CA, запись в hosts…); устройство становится выданной экземпляру целью.
- **Реестр типов** — публичный документ `docs/plugins/types.md` с контрактом данных каждого типа;
  сторонние авторы вводят свои типы с префиксом своего плагина (`<plugin-id>.<имя>`).
- Демо: `hestia-probe` (requires `http.service`, следит за hello и показывает ответ) и связь
  hello → устройство (запись `hello.home` в `/etc/hosts` устройства).
- Зависимости в мастере создания: для каждого обязательного `requires` — выбрать существующий
  совместимый экземпляр или «Создать новый» (вложенный мастер: этот же сервер или другой); всё —
  одним планом.
- Карта: внутри сервера/гостя — экземпляры (подузлы) и контейнеры их проектов; `provides` — ручки на
  границе; позиции, которые пользователь двигал, сохраняются.

## Модель

### Порты (манифест, расширение `provides`/`requires` из 02h)

```json
"provides": [
  {"name": "web", "type": "http.service", "label": "Веб-страница",
   "client": true, "multi": true}
],
"requires": [
  {"name": "target", "type": "http.service", "label": "Что проверять",
   "optional": false, "multi": false}
]
```

- `name` — `^[a-z][a-z0-9_]{0,31}$`, уникален в своём списке; если не указан (манифесты 02h) —
  `= type` с заменой `.`/`-` на `_` (совместимость).
- `provides.multi` (по умолчанию `true`) — может ли порт обслуживать много потребителей.
- `provides.client` — поставщик умеет связь «сервис → устройство» для этого порта.
- `requires.optional` (по умолчанию `false`), `requires.multi` (по умолчанию `false`) — сколько
  поставщиков можно подключить.
- `type`: официальные типы из реестра (без точки-префикса плагина) или `<plugin-id>.<имя>` для
  собственных типов плагина. Неизвестный официальный тип или чужой префикс — пакет отклонён.
- Совместимость: связь допустима только при **точном** совпадении `type` (без иерархий в 2a-2).

### Реестр типов (`docs/plugins/types.md` + `sdk/types`)

Тип = имя, описание, версия контракта, JSON-схема `binding` (что поставщик отдаёт потребителю) и
`client` (что поставщик делает на устройстве — словами, для UI). В 2a-2 официально вводятся:

| Тип | binding | client |
|---|---|---|
| `http.service` | `{url, host, port, scheme}` | — |
| `ca.issuer` | `{ca_pem, acme_url?, issue: "rpc"}` (детали — 2a-3) | доверие к CA на устройстве |
| `postgres.db` | `{host, port, database, user, password: secret}` | — |
| `smb.share` | `{host, share, user, password: secret, vers}` | монтирование на устройстве |
| `fs.media` | `{path}` (каталог, видимый потребителю; источник — smb/локальный) | — |

`sdk/types` — Go-структуры и валидаторы для официальных типов (Hestia валидирует `binding` поставщика
по схеме до передачи потребителю; ошибка → связь `failed`). Поля `secret` передаются как ссылки на
секрет (`{"secret": "<id>"}`), потребитель читает значение через `secret.get` — только если связь
активна (см. «Права»).

### Связь (link)

```
link: id, kind (service|device),
      provider: {instance, port},
      consumer: {instance, port}            -- kind=service
      device:   {ref: ssh:<id> | lxc:<id>:<node>:<vmid>}   -- kind=device
      config (JSON, по схеме link_schema порта поставщика, необязательно),
      binding (JSON, без значений секретов), status, detail, created_at, checked_at
```

- Для `device` устройство добавляется в гранты **экземпляра-поставщика** с пометкой `via_link`
  (грант живёт, пока жива связь).
- `provides[].link_schema` (необязательно) — поля формы связи (тот же формат, что `schema.fields`,
  без `target`), например имя в hosts или точка монтирования.

### Жизненный цикл связи

Создание/удаление связи — всегда план → подтверждение → задача `plugin-link` (шаги и лог обоих
плагинов в одной задаче), как экземпляры 02h (хеш плана, 15 мин, перепроверка перед apply).

**service:**
1. `link.plan` у поставщика (`{link, role: "provider", port, consumer: {plugin, instance, port}, config}`)
   и у потребителя (`role: "consumer"`, без binding) → действия обеих сторон объединяются в один план,
   с подписью стороны («Postgres 1: создать базу iris», «Iris 1: переподключиться»).
2. apply: поставщик `link.apply` → возвращает `binding`; Hestia валидирует по типу, секреты из
   binding кладёт в secrets связи (`link:<id>:<name>`), потребителю отдаёт binding со ссылками →
   `link.apply` потребителя. Ошибка потребителя → `link.remove` у поставщика (откат), связь `failed`
   с текстом, запись удаляется.
3. Удаление: `link.remove` у потребителя, затем у поставщика; секреты связи удаляются.
   Ошибка поставщика при удалении → связь `orphaned` (видна, кнопка «Удалить запись»).

**device:**
1. `link.plan` у поставщика с `role: "client"`, `device` (ref + сведения из `target.list`), `config`.
2. apply: `link.apply` у поставщика — работает на устройстве через `target.exec`/`put_file` (грант
   устройства действует с начала apply).
3. Удаление — `link.remove` у поставщика, затем грант `via_link` снимается.

**Статус:** `link.status` у обеих сторон (поставщик и, для service, потребитель) при открытии карты и
раз в 5 мин; итог — худший (`ok/degraded/down/unknown`). На карте — цвет ребра.

**Изменение экземпляра** (02h `update`): если у экземпляра есть связи, Hestia после успешного apply
вызывает `link.refresh` у поставщика по каждой его связи (binding мог измениться: порт, адрес) и,
если binding изменился, `link.apply` у потребителя с новым binding. **Удаление экземпляра** со
связями — план включает удаление всех его связей (сначала связи, потом экземпляр).

### Методы плагина (Hestia → плагин), протокол v1 (расширение, без смены версии)

| Метод | Назначение |
|---|---|
| `link.plan {link, role, port, peer?, device?, config}` | действия своей стороны |
| `link.apply {job_id, link, role, port, peer?, device?, config, binding?}` | provider → `{binding}`; consumer/client → `{}` |
| `link.remove {job_id, link, role, …}` | убрать свою сторону |
| `link.status {link, role, …}` | `{state, detail}` |
| `link.refresh {link}` | provider → `{binding}` (после изменения экземпляра) |

Если плагин объявил порт, но не реализует `link.*` (`-32601`) — связь с этим портом недоступна, UI
показывает «плагин не поддерживает связи». Манифест с портами и `"protocol": 1` без методов — валиден
(совместимость с hello v0.2.0).

### Права и доступ

- Новое право **`links.client`** — нужно поставщику для связей `device` (работа на чужих устройствах).
  Без него `client: true` в манифесте — ошибка пакета.
- `target.exec/put_file/deploy.*` по устройству связи — только во время `link.*` этой связи и пока
  связь существует (грант `via_link`), плюс право `targets.exec` у плагина.
- `secret.get` секретов связи (`link:<id>:*`) — только потребителю этой связи и только пока связь
  активна; поставщик пишет их только через `binding` в `link.apply`/`link.refresh` (не через
  `secret.put`).
- Плагин не видит чужие экземпляры, кроме `peer` в вызовах `link.*` (id, plugin, имя, порт).

## Зависимости при создании экземпляра

- Мастер создания (02h) получает шаг **«Зависимости»** перед планом, если у плагина есть
  `requires` (обязательные — сразу, необязательные — под «Подробнее»).
- Для каждого `requires`: список совместимых портов `provides` существующих экземпляров (имя, где
  стоит, статус; несовместимые не показываются; поставщик с `multi: false`, уже занятый, — серым) +
  «Создать новый <плагин>» (если поставщиков несколько плагинов — выбор плагина; если ни одного не
  установлено — ссылка «Установить из каталога», без автоустановки в 2a-2).
- «Создать новый» — вложенный мастер того же вида (форма по схеме; цель по умолчанию — **та же, что
  у создаваемого экземпляра**, переключатель «другой сервер»). Глубина вложенности ≤ 3; цикл
  (тот же плагин по цепочке) запрещён.
- **Составной план** (`composite plan`): упорядоченный список шагов — создание новых
  поставщиков → создание экземпляра → связи. Каждый шаг — свой `instance.plan`/`link.plan`; общий хеш.
  Применение одной задачей `plugin-compose`; при ошибке — откат в обратном порядке уже применённых
  шагов (`link.remove`, `instance` `remove`). В плане видно, что будет откатываться.
- Связь при создании потребителя: потребитель в `instance.plan` получает `links: [{port, peer}]`
  (что будет подключено), а `binding` — уже в `link.apply` после создания.

## Карта

### Модель для UI

`GET /api/v1/graph` — единый граф (хосты из 02f + экземпляры + связи):

```json
{
  "hosts": [...],                       // как /network, + "ref": "lxc:1:pve1:901" | "ssh:3" | null
  "instances": [{"id", "plugin_id", "plugin_name", "name", "icon_url", "status",
                 "host_ref", "host_ip", "provides": [...], "requires": [...],
                 "containers": [{"name", "image", "state", "ports"}]}],
  "links": [{"id", "kind", "provider": {"instance","port"}, "consumer": {...} | null,
             "device": {"ref","host_ip"} | null, "status", "detail"}],
  "positions": {"<node id>": {"x", "y"}}
}
```

- `host_ref` экземпляра — его цель (первый грант типа `target`, не `via_link`); хост на карте —
  по ref → IP из инвентаря (как 02f «Связь с инвентарём»). Экземпляр без найденного хоста — в группе
  «Без хоста».
- `containers` — из последнего `deploy.status` (кеш в БД при status-проверке экземпляра; без root-пути
  при открытии карты).

### Отображение

- Хост с экземплярами/контейнерами — **составной узел**: шапка (как сейчас: имя, IP, статус, значки),
  внутри — подузлы экземпляров (иконка плагина, имя, статус-рамка), внутри экземпляра — строки
  контейнеров (имя, образ, состояние). Хост без экземпляров — как сейчас (обычная карточка).
- Порты: у подузла экземпляра — ручки `provides` (справа) и `requires` (слева) с подписью `label`;
  незакрытый обязательный `requires` — красная ручка. На границе составного узла дублируются ручки
  `provides` экземпляров («выведенные наружу»): связь к сервису на другом хосте рисуется от ручки
  на границе; внутри хоста — между подузлами.
- Связи — рёбра: service — сплошное от provides к requires; device — пунктир от provides к карточке
  хоста. Цвет — статус. Подпись — тип (по наведению — detail).
- **Тянуть связь:** drag от ручки `provides` → на совместимую ручку `requires` (подсветка совместимых
  при начале перетаскивания, несовместимые — тусклые) или на хост (если `client: true` и хост
  выдаваемый: ssh/lxc из кандидатов целей) → боковая панель «Новая связь»: стороны, форма
  `link_schema`, «Показать план» → план → «Применить» → задача (прогресс в панели).
- Клик по ребру — панель связи: стороны, статус, detail, «Проверить», «Удалить» (план → задача).
- Клик по экземпляру — панель: статус, endpoints, связи, ссылка на страницу плагина.
- **Позиции:** перетаскивание узла (хоста или группы) сохраняет его позицию (`PUT /api/v1/graph/positions`,
  debounce 1 с); узлы без сохранённой позиции раскладываются как сейчас (dagre/сетка), сохранённые —
  на своих местах. Кнопка «Разложить заново» сбрасывает сохранённые позиции (с подтверждением).
  Подузлы внутри составного — всегда авто (сетка), не сохраняются.

### Страница плагина / экземпляра

- У экземпляра — блок «Связи» (список, статус, «Удалить», «Связать…» — та же панель, что на карте,
  с выбором второй стороны списком).
- Карточка плагина: явная кнопка **«Экземпляры (N)»** (замечание живой проверки 2a-1).

## Демо-плагины

### hestia-hello v0.3.0

- `provides: [{name: "web", type: "http.service", label: "Веб-страница", client: true,
  link_schema: {fields: [{name: "hostname", type: "string", label: "Имя", default: "hello.home",
  pattern: "^[a-z0-9.-]{1,63}$"}]}}]`; права + `links.client`, `targets.exec`.
- `link.apply` provider/service → binding `http.service` (`url`, `host` = IP цели, `port`, `scheme`).
- `link.*` client/device: строка `<IP цели hello> <hostname> # hestia-link-<link id>` в `/etc/hosts`
  устройства (добавить/заменить по маркеру, удалить по маркеру; файл правится атомарно через
  временный файл + `mv`, права/владелец сохраняются). Status: строка на месте и резолвится
  (`getent hosts <hostname>`).
- `link.refresh` — новый binding после изменения порта; client-связи при смене IP — обновить строку
  (Hestia вызывает `link.apply` client заново, если binding поставщика изменился).

### hestia-probe v0.1.0 (новый, `plugins/hestia-probe`)

- Без цели и без Docker: работает внутри своей песочницы (`net.outbound`). Схема: `interval_s`
  (30…3600, по умолчанию 60).
- `requires: [{name: "target", type: "http.service", label: "Что проверять"}]` — обязательный,
  `multi: false`.
- `instance.plan/apply` — только запись конфигурации (действий на целях нет; план «Создать проверку»).
- `link.apply` consumer — запоминает binding (в своём `StateDirectory`), начинает опрос `url`;
  `instance.status` — `ok` + detail «200, 12 мс, Name: Привет от Hestia» (первая строка тела `Name:`),
  `down` при ошибке; endpoint — ссылка на проверяемый URL.
- Без связи `instance.status` → `degraded` «Не подключён к сервису».
- Для мастера зависимостей: создание probe предлагает выбрать существующий hello или «Создать новый
  Hestia Hello» (вложенный мастер с целью).

## Данные (миграция)

```sql
CREATE TABLE plugin_links (id INTEGER PRIMARY KEY, kind TEXT NOT NULL CHECK (kind IN ('service','device')),
  provider_instance INTEGER NOT NULL REFERENCES plugin_instances(id),
  provider_port TEXT NOT NULL,
  consumer_instance INTEGER REFERENCES plugin_instances(id), consumer_port TEXT,
  device_ref TEXT,
  config TEXT NOT NULL DEFAULT '{}', binding TEXT NOT NULL DEFAULT '{}',
  status TEXT NOT NULL DEFAULT 'unknown', detail TEXT NOT NULL DEFAULT '',
  created_at INTEGER NOT NULL, checked_at INTEGER,
  CHECK ((kind='service' AND consumer_instance IS NOT NULL AND device_ref IS NULL)
      OR (kind='device' AND consumer_instance IS NULL AND device_ref IS NOT NULL)));
CREATE UNIQUE INDEX plugin_links_service ON plugin_links(provider_instance, provider_port, consumer_instance, consumer_port) WHERE kind='service';
CREATE UNIQUE INDEX plugin_links_device ON plugin_links(provider_instance, provider_port, device_ref) WHERE kind='device';
ALTER TABLE plugin_grants ADD COLUMN via_link INTEGER REFERENCES plugin_links(id) ON DELETE CASCADE;
ALTER TABLE plugin_instances ADD COLUMN containers TEXT NOT NULL DEFAULT '[]';
CREATE TABLE map_positions (node_id TEXT PRIMARY KEY, x REAL NOT NULL, y REAL NOT NULL, updated_at INTEGER NOT NULL);
```

(первичный ключ `plugin_grants` с `via_link` — пересоздать таблицу, если нужно; батч решает и
отмечает в «Отклонениях»). Время — INTEGER мс, как во всей базе.

## Тесты

- Манифест: порты с/без `name`, неизвестный тип, чужой префикс, `client` без `links.client`, дубли имён.
- Типы: валидация binding официальных типов; секретные поля → ссылки; потребитель читает секрет связи
  только пока связь активна, чужой связи — отказ; поставщик не может `secret.put` в `link:*`.
- Связи service/device: план обеих сторон, apply, откат при ошибке потребителя, удаление, `orphaned`,
  refresh после update экземпляра, удаление экземпляра со связями, `multi: false` занятый порт,
  несовместимые типы, плагин без `link.*`.
- Гранты `via_link`: доступ к устройству только во время/после создания связи, снятие при удалении,
  тест на вызов к устройству чужой связи.
- Составной план: 0/1/2 уровня новых поставщиков, цикл, глубина > 3, ошибка на каждом шаге → откат
  ранее применённых в обратном порядке, перепроверка хеша.
- `GET /graph`: экземпляр на LXC/SSH-цели находит свой хост, без хоста → «Без хоста», контейнеры из кеша.
- Web: построение графа с составными узлами и ручками, совместимость при drag (чистая функция),
  сохранение/сброс позиций, панель связи, шаг «Зависимости» мастера.
- E2E (dev-режим, **оба** демо-плагина через `--plugin-dev` — флаг становится повторяемым): hello на
  фейковой SSH-цели (deploytest) → probe через мастер с «создать новый hello» одним планом → связь
  hello → устройство (вторая фейковая цель, `/etc/hosts` под временным корнем) → статусы → удаление
  экземпляра hello удаляет обе связи.

## Живая проверка (с разрешения пользователя)

1. Релиз v0.3.0, обновление CT 900; публикация hello v0.3.0 и probe v0.1.0 в каталог; обновление hello
   на CT 900 из каталога (проверка «Обновить до» и новых прав).
2. Одноразовые CT 901 (hello, Docker) и CT 902 (устройство для hosts) на pve1 — создаю по слову
   пользователя, после проверки удаляю.
3. Мастер probe → «создать новый hello на CT 901» одним планом → probe `ok` с ответом whoami.
4. На карте: CT 901 — составной узел с hello и контейнером whoami, probe — в «Без хоста» (или у
   контроллера — см. ниже), связь hello → probe; тянем hello → CT 902 → `getent hosts hello.home` на 902.
5. Двигаем узлы, перезагрузка страницы — позиции на месте; «Разложить заново».
6. Удаление hello → план удаляет обе связи; probe → `degraded`.

Где на карте показывать экземпляры без цели (probe работает на контроллере): в составном узле
**контроллера Hestia** (хост CT 900 по IP из `remote`/health), а если хост контроллера на карте не
найден — в группе «Без хоста».
