# 02g. Этап 1f — AdGuard Home → `hestia.home`

Цель: если в сети найден AdGuard Home, Hestia предлагает дать себе DNS-имя (`hestia.<зона>`,
по умолчанию `hestia.home`), прописывает rewrite в AdGuard по подтверждению, проверяет его и дальше
открывается по имени (HTTP; сертификат — позже, плагин CA). Это первый «зачаток» DNS-плагина:
подключение к AdGuard сохраняется и пригодится ему.

## Решения (2026-11-18, с пользователем)

- Доступ к API AdGuard: если у хоста AdGuard есть HTTPS (обычно nginx перед ним, сертификат
  домашнего CA) — через HTTPS с **закреплением отпечатка** сертификата после подтверждения
  пользователем (как у Proxmox в 1b); иначе — HTTP на порт веб-интерфейса AdGuard (3000/9091/80...)
  с явным предупреждением «пароль пойдёт по сети открытым текстом».
- Логин/пароль администратора AdGuard сохраняются **зашифрованно** (secrets, master.key):
  нужны для обновления записи и будущего DNS-плагина.
- Если IP контроллера сменился (DHCP), а запись указывает на старый — **предупреждение и кнопка
  «Обновить запись»** (план + подтверждение). Без автоисправления.
- Desktop-клиент после успешной проверки имени **переключается на `http://<имя>`**, IP остаётся
  запасным адресом (у ПК может быть второй DNS-сервер, который `.home` не знает).

## Обнаружение

- Источник — последний скан (1e-2): сервисы с `id = "adguard"`. Эндпоинты одного хоста
  (например `https://<ip>:443` за nginx с редиректом на `/login.html` и `http://<ip>:9091`)
  сводятся в один экземпляр AdGuard. Порядок предложения: HTTPS → HTTP.
- Несколько хостов с AdGuard — список, выбирает пользователь (по умолчанию первый по IP).
- Нет скана или нет AdGuard — карточка «AdGuard не найден» с кнопкой «Указать адрес вручную»
  (URL) — для AdGuard в подсети, которая не сканируется.

## Подключение (ничего не меняет в AdGuard)

1. Проба эндпоинта (без пароля): для HTTPS — отпечаток SHA-256 листового сертификата, subject,
   issuer, SAN, срок; `GET /control/status` → ожидается 401 (или 200 без авторизации — тогда
   предупреждение «AdGuard без пароля»).
2. Пользователь видит отпечаток (как в 1b) и вводит логин/пароль. Проверка: `GET /control/status`
   с HTTP Basic → 200, `version`, `running`, `dns_port`, `dns_addresses`; `GET /control/rewrite/settings`
   → `enabled` (если `false` — предупреждение: rewrite в AdGuard выключены, запись не будет работать).
3. Сохранение: подключение + закреплённый отпечаток + пароль в secrets (purpose `adguard:<id>`).
   Пароль не попадает в журнал задач, логи и ответы API (только `has_password: true`).
- TLS: проверка цепочки и имени НЕ делается, только совпадение отпечатка (сертификаты домашнего CA,
  обращение по IP). Несовпадение → ошибка «Сертификат AdGuard изменился» с новым отпечатком и кнопкой
  «Доверять новому» (повторное подтверждение). Пустой пин для HTTPS недопустим.
- Таймауты: 5 с на запрос, редиректы не следовать (кроме проверки пробы — только показать Location).

## Имя Hestia: план → применение → проверка

- Домен по умолчанию: `hestia.<зона>`, зона — самый частый суффикс среди существующих rewrite вида
  `<имя>.<зона>` (без `*`), при отсутствии — `home`. Поле редактируемое; проверка — валидное
  DNS-имя (буквы/цифры/дефис, ≤ 253, без `*`).
- Ответ (IP): адрес контроллера, **как его видит AdGuard** — локальный адрес TCP-соединения
  контроллера к эндпоинту AdGuard. Показывается в плане, не редактируется. Если контроллер работает
  на ПК (desktop до самоустановки) — предупреждение «Hestia пока работает на этом компьютере;
  лучше сначала перенести её на сервер», но не запрет.
- План (`POST /api/v1/dns/plan`): `GET /control/rewrite/list` →
  - точная запись `domain` с тем же `answer` → «уже есть», действие не нужно (только привязать);
  - точная запись с другим `answer` → конфликт: показать, чей это IP (хост из скана/инвентаря),
    действие «заменить» только по отдельному подтверждению;
  - wildcard, накрывающий имя (`*.home`) → предупреждение (точная запись в AdGuard имеет приоритет);
  - иначе — действие «добавить `domain → IP`».
- Применение — задача `dns-name` (jobs + SSE) по подтверждённому плану (план с хешем; если на момент
  применения `rewrite/list` изменился — отказ «план устарел»):
  1. `POST /control/rewrite/add {domain, answer, enabled: true}` (или `PUT /control/rewrite/update
     {target, update}` при подтверждённой замене).
  2. Проверка: DNS-запрос A `domain` напрямую к AdGuard (`<хост>:<dns_port>`, UDP, таймаут 2 с,
     до 5 попыток с паузой 1 с — у AdGuard кеш) → ответ равен IP контроллера.
  3. Проверка: `GET http://<IP контроллера>/api/v1/health` с заголовком `Host: <domain>` → наш
     `instance_id`.
  4. Неудача шага 2/3 → откат: удалить добавленную запись (`POST /control/rewrite/delete`) или
     вернуть прежнюю (`update` обратно); задача — «ошибка» с причиной.
  5. Успех → запись в БД (имя, ответ, когда проверено).
- Убрать имя: кнопка «Убрать запись» → план («удалить `domain → IP` из AdGuard») → задача с удалением
  только если запись в AdGuard совпадает с нашей; иначе только отвязать в Hestia.

## Слежение за записью

- Раз в 30 мин и при старте (через 1 мин) — без изменений в AdGuard: `rewrite/list` + текущий IP
  контроллера. Статусы: `ok`, `ip_changed` (запись указывает на старый IP — кнопка «Обновить запись»
  → план `update` → задача, как выше), `missing` (запись удалена в AdGuard — кнопка «Восстановить»),
  `changed` (запись указывает на чужой IP), `auth_failed`, `cert_changed`, `unreachable`.
- Статус показывается в «Системах» (карточка контроллера) и в «Сервисах» у AdGuard; пункт навигации
  без счётчиков/уведомлений (уведомления — позже).

## Хранение (миграция)

```
CREATE TABLE integrations (
  id INTEGER PRIMARY KEY,
  kind TEXT NOT NULL,              -- 'adguard'
  name TEXT NOT NULL,              -- отображаемое, по умолчанию 'AdGuard Home (<host>)'
  base_url TEXT NOT NULL,          -- https://<ip> или http://<ip>:<port>
  tls_pin TEXT NOT NULL DEFAULT '',-- sha256 листового сертификата (hex), обязателен для https
  username TEXT NOT NULL,
  secret_id INTEGER NOT NULL REFERENCES secrets(id),
  version TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);
CREATE TABLE dns_names (
  id INTEGER PRIMARY KEY,
  integration_id INTEGER NOT NULL REFERENCES integrations(id) ON DELETE CASCADE,
  domain TEXT NOT NULL UNIQUE,
  answer TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'ok',
  status_detail TEXT NOT NULL DEFAULT '',
  verified_at TEXT, checked_at TEXT, created_at TEXT NOT NULL
);
```
В 1f — одно имя на контроллер (UNIQUE достаточно; API отдаёт его как «имя Hestia»). Удаление
подключения AdGuard удаляет и secret.

## API (всё с входом, кроме health)

- `GET /api/v1/dns` → `{candidates:[{host, endpoints:[{url, scheme, port}]}], integration: {...|null},
  name: {domain, answer, status, status_detail, verified_at, checked_at}|null, controller_ip}`.
- `POST /api/v1/dns/adguard/probe {url}` → `{url, tls:{sha256, subject, issuer, san[], not_after}|null,
  status_code, location, warning}`.
- `POST /api/v1/dns/adguard {url, tls_pin, username, password}` → проверка (шаг 2) и сохранение;
  `PUT` то же для смены пароля/пина; `DELETE /api/v1/dns/adguard`.
- `POST /api/v1/dns/plan {action: "add"|"replace"|"update_ip"|"remove", domain}` → `{plan_id, hash,
  domain, answer, actions:[...], conflicts:[...], warnings:[...]}`.
- `POST /api/v1/dns/apply {plan_id, hash}` → `{job_id}`.
- `GET /api/v1/health` добавляет `"dns_url": "http://<domain>"`, только когда имя в статусе `ok`
  (публичная информация; без входа).

## Desktop (ПК-клиент)

- `remote.json` получает поле `fallback_url`. При старте в режиме moved: проверить `url`, при неудаче —
  `fallback_url`, открыть первый ответивший с тем же `instance_id`.
- Переключение: при старте, если health контроллера отдаёт `dns_url`, текущий `url` — не он, имя
  резолвится на ПК (системный резолвер, таймаут 2 с) и `GET <dns_url>/api/v1/health` даёт тот же
  `instance_id` → записать `url = dns_url`, `fallback_url = прежний url` (атомарно, 0600). Иначе
  ничего не менять. Если `dns_url` пропал — remote.json не трогать (запасной адрес работает и так).
- Только Linux-путь, без GUI-изменений: в «Системах» строка «Адрес: http://hestia.home (запасной:
  http://<ip>)», если это клиент.

## Интерфейс

- «Системы», карточка контроллера: блок «Имя в сети». Нет AdGuard в скане → скрыт (или ссылка
  «Указать AdGuard вручную»). Есть AdGuard, нет подключения → «Найден AdGuard Home на <ip>. Дать Hestia
  имя `hestia.home`?» → кнопка «Настроить».
- Мастер (модальное окно, шаги с разумными умолчаниями):
  1. Эндпоинт (радио, по умолчанию HTTPS) + отпечаток сертификата («Это сертификат вашего AdGuard?»)
     или предупреждение про HTTP.
  2. Логин (по умолчанию пусто) / пароль. Проверка.
  3. Имя (`hestia.home`, редактируемое) → план: что будет сделано, IP, конфликты/предупреждения.
  4. «Применить» → прогресс задачи (SSE) → итог с кнопкой «Открыть http://hestia.home».
- «Сервисы»: у строки AdGuard значок «подключён» и ссылка на блок имени.

## Безопасность

- Пароль AdGuard: только в secrets (AES-GCM), не логировать, не отдавать в API, маскировать в ошибках
  (ошибки HTTP-клиента не должны содержать URL с userinfo).
- Любое изменение AdGuard — только через план + подтверждение (`plan_id` + `hash`), с откатом.
  Hestia меняет/удаляет только запись своего имени.
- HTTPS без закреплённого отпечатка не используется; `InsecureSkipVerify` допустим только вместе
  с проверкой пина в `VerifyConnection`.
- Слежение — только GET.

## Тесты

- Фейковый AdGuard (`httptest`, HTTP и TLS) по `openapi.yaml` v0.107: Basic auth (401 без/с неверным
  паролем), `status`, `rewrite/list|add|delete|update|settings`; фейковый DNS-сервер на
  `127.0.0.1:0` (UDP, miekg/dns не тянуть — минимальный ответ на A можно собрать руками или
  `golang.org/x/net/dns/dnsmessage`).
- Зона по умолчанию: набор rewrite → `home`; пусто → `home`; wildcard и имена без точки игнорируются.
- План: нет записи → add; та же → no-op; другой IP → конфликт; wildcard → предупреждение; устаревший
  хеш → отказ.
- Применение: успех; DNS отвечает не тем IP → откат удаляет запись; health с чужим instance_id → откат;
  replace → откат возвращает прежний ответ.
- Пин: верный → ок; другой сертификат → `cert_changed`, запросов с паролем не было.
- Пароль не встречается в журнале задач, логах, ответах API (поиск строки по всем выводам теста).
- Слежение: ip_changed / missing / changed / auth_failed.
- Desktop: remote.json переключение и fallback (без GUI, функцией).
- Фронтенд: редьюсер/форматирование статусов, валидация домена.

## Критерий (проверяет ревьюер на живой сети, с разрешения пользователя на запись)

- Проба HTTPS-эндпоинта AdGuard → отпечаток совпадает с `openssl s_client | openssl x509 -fingerprint
  -sha256`. Подключение и план — только чтение.
- Применение на живом AdGuard — **только после явного «да» пользователя**: `dig +short hestia.home
  @<adguard>` → IP контроллера; `curl http://hestia.home/api/v1/health` с ПК → instance_id контроллера.
- Desktop после перезапуска открывается на `http://hestia.home`.
