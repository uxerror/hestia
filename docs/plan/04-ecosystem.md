# 04. Экосистема плагинов и граф связей

Главная ценность Hestia — не карта сети и не набор интеграций, а **экосистема**: Hestia ставится
один раз и дальше через свои плагины настраивает и контролирует сервисы и сеть. Если для чего-то
есть плагин Hestia, она работает с этим целиком, без ручной доработки. Плагины может писать любой.

Интеграции без плагина (как AdGuard на этапе 1f) остаются: Hestia показывает и умеет базовые вещи,
но «идеальная» работа — через плагин.

## Плагины (первый набор)

| Плагин | Основа | Что даёт Hestia поверх |
|---|---|---|
| HestiaCA | свой CA на Go (код certbot), новый корень Hestia | выпуск, продление, раздача доверия; HTTPS для самой Hestia и сервисов |
| HestiaDNS | BIND9 | зоны из GUI, списки блокировок, разрешённые/запрещённые сайты; первичный или вторичный DNS |
| HestiaSMB | Samba | шары с пресетами, пользователи, подключение к устройствам связью на карте |
| HestiaBox | MikroTik (позже другие роутеры) | DHCP-резервации, leases/ARP, смена IP прямо с карты |
| HestiaIris | Iris | ставит Iris с зависимостями (Samba, Postgres), связывает их |

## Модель: сервис предоставляет / требует

- Экземпляр плагина = **сервис** (узел графа) с **портами связи**: `provides` (например
  `smb.share`, `postgres.db`, `dns.resolver`, `ca.issuer`) и `requires` (Iris: `fs.media`,
  `postgres.db`).
- **Связь** (ребро графа) соединяет `requires` одного узла с `provides` другого совместимого типа.
  Нарисовать связь на карте = попросить Hestia её реализовать: Samba ↔ ПК → Hestia монтирует шару
  на ПК (через агент); Samba ↔ Iris → Iris получает путь/креды; CA ↔ сервис → сервис получает
  сертификат и доверие.
- Каждая связь реализуется плагинами обеих сторон через план → подтверждение → применение →
  проверка → откат (как все изменения Hestia).
- Зависимости при установке: плагин объявляет `requires`; мастер предлагает взять существующий
  совместимый сервис, поставить новый на тот же сервер или на другой.

## Мультиграф сервера

- Сервер (VM/LXC/хост) с несколькими сервисами показывается как **составной узел**: внутри —
  подграфы сервисов (например Iris + Samba + Postgres в Docker) и связи между ними.
- Порт внутреннего сервиса можно **вывести на границу** составного узла и связать на общей
  карте с другим сервером или сервисом (Samba внутри узла Iris → шара для ПК).
- Если зависимости на разных серверах — это обычные связи между узлами; модель одна.

## Техника плагинов

- Плагин — **отдельный процесс**, Hestia общается с ним по RPC (подход HashiCorp go-plugin).
  SDK на Go; первые плагины (CA, DNS, SMB, Box) пишутся на том же SDK, без привилегий
  встроенного кода. Падение плагина не роняет контроллер.
- Плагин описывает манифестом: имя, версия, автор, `provides`/`requires`, схема полей и пресеты
  (UI строит формы без кода во фронтенде), запрашиваемые **права** (какие цели, сети, секреты,
  root на целях, Docker).
- Hestia даёт плагину API хоста: транспорт к целям (SSH/Proxmox, только к разрешённым), секреты,
  задачи (jobs + лог + SSE), инвентарь и граф, шаблоны развёртывания.
- **Размещение сервисов:** по умолчанию Docker (compose) на выбранном сервере/LXC; плагин может
  объявить нативную установку, если Docker не подходит.
- **Доверие:** плагины подписаны автором (ed25519). Официальные (ключ uxerror) ставятся сразу;
  сторонние — с предупреждением и списком прав, которые плагин просит.

## DNS: AdGuard и HestiaDNS

- Hestia работает с двумя DNS одновременно; HestiaDNS может быть первичным или вторичным.
- При установке HestiaDNS рядом с AdGuard Hestia предлагает **перенести настройки и удалить
  AdGuard**. Сценарий (с HestiaBox и по подтверждению каждого шага):
  1. перенести rewrite/списки в HestiaDNS;
  2. удалить гостя AdGuard на Proxmox;
  3. поставить HestiaDNS в LXC или VM (выбор пользователя);
  4. через HestiaBox закрепить за новым гостем IP старого AdGuard (клиентам ничего менять не надо).
- Без HestiaBox шаг с IP — ручной, с точной подсказкой (как резервация контроллера сейчас).
- Дальше IP сервисов меняются прямо с карты (HestiaBox правит резервацию, Hestia — DNS-записи).

## Этапы

1. **2a. Каркас плагинов + граф связей + HestiaCA → HTTPS для Hestia** (первый этап экосистемы):
   RPC-хост и SDK, манифест/права/подпись, установка и обновление плагинов, модель
   provides/requires и связи на карте, составной узел сервера, Docker-развёртывание;
   HestiaCA как первый плагин; Hestia переходит на HTTPS (desktop пиннит/доверяет CA).
2. HestiaBox (MikroTik) — нужен для сценариев с IP.
3. HestiaDNS (+ перенос с AdGuard).
4. HestiaSMB + агент ПК (связь «шара ↔ устройство» = монтирование).
5. HestiaIris (зависимости, мультиграф в деле).

Каждый этап — отдельная спека `02x-*.md` перед реализацией.
