# 02e. Этап 1u — обновление контроллера

Цель: обновлять установленный контроллер (LXC или отдельный сервер, этап 1c) двумя путями:
1. **Из приложения (офлайн).** Пользователь открывает desktop-приложение новой версии; оно видит,
   что контроллер старше, и предлагает обновить. Бинарник берётся из самого приложения (payload,
   этап 1c), интернет не нужен.
2. **С GitHub.** Контроллер раз в сутки (и по кнопке) проверяет релизы `uxerror/hestia`, при
   наличии новой версии показывает уведомление; установка — по кнопке. Релиз принимается только
   с верной ed25519-подписью.

Обновление атомарно: при сбое нового бинарника возвращаются прежний бинарник и база.

## Решения (2026-11-18, с пользователем)

- Версии — теги `vX.Y.Z`; версия сборки = `git describe --tags --always --dirty`
  (`v0.1.0`, `v0.1.0-5-gabc1234`, `v0.1.0-5-gabc1234-dirty`). Тег `v0.1.0` ставится на коммит
  этого этапа. Сравнение: (major, minor, patch, commits-since-tag); `-dirty` — то же число, но
  помечено «сборка с незакоммиченными изменениями». Нетеговые версии (`dev`, голый хеш) не
  сравнимы: обновить можно только с подтверждением «версия неизвестна».
- Предлагается только **более новая** версия. Равная или старшая — нет (кроме ручной установки
  нетеговой/dirty-сборки с предупреждением; даунгрейд запрещён всегда).
- GitHub: только уведомление, установка по кнопке. Проверка раз в 24 ч (первая — через 1 мин после
  старта) + кнопка «Проверить сейчас». Источник — `https://api.github.com/repos/uxerror/hestia/releases/latest`
  (repo задаётся `-ldflags -X …updateRepo=`, по умолчанию `uxerror/hestia`). Без токена GitHub;
  ошибки сети — тихо в статус «не удалось проверить: …».
- Подпись: ed25519. Приватный ключ — у пользователя локально (`~/.config/hestia/release.key`, 0600);
  публичный — в репозитории `internal/update/release.pub` (embed). `make release` собирает,
  подписывает и выкладывает через `gh`. Если `release.pub` пустой (ключ ещё не создан), канал
  GitHub в UI показан как «не настроен».

## Формат релиза

Ассеты релиза `vX.Y.Z`:
- `hestia-linux-amd64` — серверный статический бинарник (`CGO_ENABLED=0`);
- `hestia-desktop-linux-amd64` — desktop-сборка (с payload);
- `SHA256SUMS` — строки `<sha256>  <имя>` для двух файлов выше;
- `SHA256SUMS.sig` — base64 ed25519-подписи файла `SHA256SUMS` целиком.

Проверка на контроллере: подпись `SHA256SUMS` публичным ключом → sha256 скачанного
`hestia-linux-amd64` совпал → `version` нового бинарника = тег релиза. Любое несовпадение — отказ.

## Инструмент релиза (`cmd/hestia-release`, в бинарник Hestia не входит)

- `hestia-release keygen [--out ~/.config/hestia/release.key]` — создать ключ (отказ, если файл есть),
  записать приватный 0600, вывести публичный (base64) и записать его в `internal/update/release.pub`.
- `hestia-release sign <dir>` — посчитать SHA256SUMS по файлам в `<dir>`, подписать, записать `.sig`.
- `hestia-release verify <dir>` — проверить тем же кодом, что использует контроллер.
- `make release VERSION=vX.Y.Z`: проверки (дерево чистое, HEAD = тег `VERSION`, тесты) → `make web
  server desktop` в `dist/` → `hestia-release sign dist` → `hestia-release verify dist` →
  `gh release create VERSION dist/* --notes-from-tag` (или `--generate-notes`). Без `gh auth` —
  остановиться перед выкладкой, сообщив, что собрано в `dist/`.

## Применение обновления (общее для обоих путей)

Контроллер работает от `hestia` и не может сам заменить `/usr/local/bin/hestia` и перезапуститься,
поэтому действия от root выполняются тем же путём, что в 1c:
- LXC — SSH на узел ключом Hestia (пиннутый host key), `pct exec <vmid> -- sh -c …`;
- отдельный сервер — SSH на хост (цель 1c, root или `sudo -n`).
Где контроллер живёт — `settings.controller_location` (записан при самоустановке). Нет записи
(контроллер не устанавливался через 1c) → обновление недоступно с понятной причиной.

Задача `update` (jobs, шаги и лог как обычно):
1. **Проверка бинарника** — ELF linux/amd64, статический (как в 1c), sha256 посчитан.
2. **Загрузка** — через stdin в `/usr/local/bin/hestia.new` (0755 root), сверка sha256;
   `hestia.new version` = ожидаемая версия; проверка даунгрейда ещё раз по фактической версии.
3. **Скрипт обновления** — `/usr/local/lib/hestia/upgrade.sh` (0755 root, текст встроен в Hestia,
   кладётся каждый раз заново) и файл `/var/lib/hestia/update.json` (0600 hestia) —
   `{job_id, from, to, started_at}`.
4. **Запуск вне cgroup службы** — `systemd-run --unit hestia-upgrade-<ts> --collect
   /usr/local/lib/hestia/upgrade.sh <port>`; задача пишет «Перезапуск контроллера…» и завершается
   в памяти статусом `running` (процесс сейчас будет остановлен — это ожидаемо).

`upgrade.sh` (sh, `set -eu`, лог в `/var/lib/hestia/upgrade.log`, хранить последние 5 запусков):
1. `systemctl stop hestia`;
2. бэкап: `/var/lib/hestia/backup/<ts>/` ← `hestia.db*` + текущий `/usr/local/bin/hestia`
   (хранить 3 последних каталога);
3. `mv hestia.new hestia`, `systemctl start hestia`;
4. ждать здоровья до 60 с: `/usr/local/bin/hestia healthcheck --url http://127.0.0.1:<port>`
   (новая подкоманда: GET `/api/v1/health`, exit 0 при `status=ok` и `version` = ожидаемая);
5. не здоров → `systemctl stop hestia`, вернуть бинарник и `hestia.db*` из бэкапа (удалив `-wal/-shm`
   нового), `systemctl start hestia`, записать в `update.json` `"rolled_back": true` и причину.

При старте контроллера: если есть `update.json` —
- версия процесса = `to` → задача `job_id` помечается выполненной (шаг «Контроллер перезапущен,
  версия X»), к ней добавляется хвост `upgrade.log`, файл удаляется;
- иначе (откат) → задача ошибка «Новая версия не запустилась, возвращена X» + хвост лога.
Задача, прерванная перезапуском, не должна помечаться «прервана» обычным механизмом — её закрывает
эта логика.

База и откат: `store.Open` отказывается открывать БД со схемой новее, чем знает бинарник
(ошибка «база создана более новой версией Hestia X»), — так старый бинарник после неудачного
обновления не испортит данные; откат восстанавливает и БД.

## Путь 1: из приложения (офлайн)

- Desktop при старте с `remote.json`: `GET <remote>/api/v1/health` → `version`. Если версия
  встроенного payload новее (правила выше), desktop поднимает на loopback **помощник** и открывает
  окно на `<remote>/#/update/offer?from=<urlencoded loopback>&v=<версия>&n=<nonce>`.
- Помощник: `GET /payload/<nonce>` отдаёт payload, `GET /payload/<nonce>/meta` →
  `{version, sha256, size, dirty}`; CORS только для origin удалённого контроллера; nonce 32 байта,
  живёт, пока открыто приложение; другие пути — 404.
- SPA контроллера (`#/update/offer`): после входа показывает «Приложение новее контроллера: X → Y.
  Обновить контроллер?» (+ предупреждение для dirty) → браузер скачивает payload у помощника и
  отправляет `POST /api/v1/update/upload` (multipart или raw body, лимит 64 МБ, с входом) →
  ответ `{upload_id, version, sha256}` → `POST /api/v1/update {upload_id}` → прогресс задачи →
  после перезапуска SPA ждёт health с новой версией (до 90 с) и перезагружает страницу.
- Загруженный файл — во временный каталог в data (0700), удаляется после задачи или через 1 ч.
- Desktop старше контроллера → баннер в окне «Приложение старше контроллера (X < Y) — обновите
  приложение» (ссылка на релизы GitHub).

## Путь 2: GitHub

- Фоновая проверка в контроллере: latest release → тег сравнить с текущей версией → состояние
  `{latest, available, checked_at, error?, notes_url}` в памяти и `settings.update_check`.
- `POST /api/v1/update {source:"github", version}` → задача: скачать `SHA256SUMS`, `.sig`,
  `hestia-linux-amd64` (таймаут 5 мин, лимит 64 МБ) → проверить подпись и sha256 → дальше общие шаги.

## API (с входом, кроме health)

- `GET  /api/v1/update` → `{current, location_ok, reason?, github:{configured, latest, available,
  checked_at, error, notes_url}, running_job?}`.
- `POST /api/v1/update/check` → немедленная проверка GitHub.
- `POST /api/v1/update/upload` → `{upload_id, version, sha256, dirty}` | 400/413/422.
- `POST /api/v1/update {upload_id}` | `{source:"github", version}` → 202 `{job}`; 409 — уже идёт.
- `GET /api/v1/health` дополняется `version` (если ещё нет).

## Интерфейс

- Значок/баннер «Доступно обновление X» в шапке, когда `available`.
- Раздел «Обновление» (в «Системах», карточка контроллера): текущая версия, где работает
  (узел/VMID или хост), состояние GitHub, кнопки «Проверить сейчас», «Обновить до X»;
  история — последние задачи `update`.
- Экран `#/update/offer` для пути 1.

## Тесты

- Сравнение версий: таблица (теги, describe, dirty, dev, хеш; даунгрейд запрещён).
- Подпись: keygen → sign → verify; порча любого байта SUMS/sig/бинарника → отказ; пустой release.pub →
  «не настроен».
- GitHub: httptest-фейк API релизов и ассетов (base URL подменяется), нет новее / есть новее / битая подпись.
- Применение: фейковый SSH-узел из 1c (`pct exec`) — загрузка, sha256, version, systemd-run вызван с
  верными аргументами; LXC и отдельный сервер (root и sudo).
- `upgrade.sh` — запуск в временном каталоге с подменой путей (переменные окружения `HESTIA_ROOT`
  для тестов) и фейковыми `systemctl`/`hestia` в `PATH`: успех; новый бинарник не здоров → откат
  бинарника и БД, `rolled_back` в update.json; ротация бэкапов (3) и логов (5).
- Старт с `update.json`: успех закрывает задачу; откат — ошибка с хвостом лога.
- `store.Open` с будущей версией схемы → понятная ошибка.
- Помощник desktop: nonce, CORS только для remote origin, 404 на чужие пути (без GUI — handler-тест).
- Upload: лимит, не-ELF, динамический ELF, неверная архитектура, даунгрейд, dirty с флагом.
- Никаких обращений к реальной сети и к GitHub в тестах.

## Первый переход

Установленный контроллер (20263a1, LXC 900) обновляться ещё не умеет. Переход на v0.1.0 —
один раз вручную ревьюером с разрешения пользователя: `pct push`/stdin нового бинарника в
`hestia.new`, бэкап БД, замена, `systemctl restart hestia`, проверка health. Дальше — штатно.

## Вне этапа

Обновление desktop-приложения самим собой, обновление ОС контейнера (apt), откат по кнопке на
предыдущую версию, каналы beta.
