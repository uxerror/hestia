# 02. Этап 1 — подключение, самоустановка, обзор сети

Итог этапа: на Linux-ПК запускается Hestia, подключает Proxmox или отдельный сервер
(установка Proxmox на чистый Debian в MVP видна, но неактивна), разворачивает себя туда, показывает системы и карту сети, а если есть
AdGuard — регистрирует себя как `hestia.home` и дальше открывается в браузере. Без сертификата
(HTTP). Плагинов нет: шаг «поставить основу» пропускается.

## Поток мастера

```
Запуск desktop
  └─ Шаг 1. Что подключаем?
       ├─ (A) Готовый Proxmox — адрес узла (+ остальные узлы кластера находятся сами)
       - (B) Чистый Debian → поставить Proxmox  [в MVP: серый, «скоро»]
       └─ (C) Отдельный сервер (Linux по SSH)
  └─ Шаг 2. Доступ: пользователь + пароль или ключ → проверка → перевод на ключ/API-токен
  └─ Шаг 3. Куда ставить Hestia: узел, хранилище, ресурсы (по умолчанию 1 vCPU, 512 МБ, 4 ГБ),
            IP (DHCP/статический) — план показывается, ставим после подтверждения
  └─ Шаг 4. Самоустановка + перенос состояния → desktop переключается на удалённый контроллер
  └─ Шаг 5. Обследование сети (job с прогрессом)
  └─ Шаг 6. Основа: плагинов нет → «пока нечего ставить», дальше
  └─ Шаг 7. Найден AdGuard? → предложить DNS-имя для Hestia
  └─ Обзор: системы, ресурсы, гости, сервисы, карта сети
```

## 1a. Каркас (этап 0, spike)

- Репозиторий, `cmd/hestia`, Makefile, `web/` (Svelte 5 + Vite + Tailwind 4 + DaisyUI 5 —
  копия базовой настройки из Iris), embed `web/dist`.
- Desktop на Wails v3: собрать «hello» с тем же фронтендом (проверить сборку на Arch/Garuda,
  зависимость webkit2gtk).
- LICENSE (MIT, uxerror).
- Store (SQLite, миграции), jobs + SSE, первый админ.

Критерий: `hestia desktop` открывает окно с SPA, `hestia serve` отдаёт ту же SPA на :8080.

## 1b. Подключение целей (A и C)

- Proxmox: проверка `/api2/json/version`; вход паролем → тикет; создание `hestia@pve`,
  роли и API-токена; SSH-ключ Hestia на каждый узел; найти остальные узлы кластера.
- Отдельный сервер: SSH паролем/ключом, кладём ключ Hestia, факты (ОС, CPU, RAM, диски, docker?).
- Всё, что меняет цель (пользователь, токен, ключ), показывается списком до выполнения.

Тесты: фейковый Proxmox API (httptest) + SSH-сервер в тестах (golang.org/x/crypto/ssh).
Против живого кластера — только чтение до явного разрешения.

## 1c. Самоустановка

Детальная спецификация — 02d-stage-1c-selfinstall.md.

На Proxmox:
- шаблон LXC Debian 13 через `pveam` (скачать, если нет);
- создать непривилегированный LXC `hestia`, при создании — уникальные machine-id и host keys
  (ошибка шаблона 135 — не повторять);
- залить бинарник `hestia`, systemd-юнит `hestia serve`, порт 80 (HTTP);
- перенести БД и мастер-ключ (права 600), проверить `/api/v1/health` нового контроллера;
- desktop переключается на удалённый адрес; локальная копия состояния архивируется.

На отдельном сервере: то же, но systemd-сервис прямо на хосте (пользователь `hestia`,
каталог `/var/lib/hestia`).

Откат: при ошибке на любом шаге — удалить созданное (LXC/юнит), состояние остаётся локальным.

## 1d. Proxmox на чистый Debian (B) — после MVP

В MVP вариант (B) виден в мастере, но неактивен («скоро»). Реализация — после MVP, самое рискованное.
- Проверки: Debian 13, amd64, статический IP (или предложить сделать), hostname в /etc/hosts
  резолвится в IP, нет конфликтующих пакетов.
- Репозиторий pve-no-subscription + ключ, установка `proxmox-ve`, перезагрузка в pve-ядро.
- Сеть: перевод интерфейса в мост `vmbr0` **с откатом по таймеру** (применили → ждём
  подтверждения от Hestia по SSH N минут → нет ответа — вернуть старый конфиг).
- Дальше как (A).

Тестировать только на одноразовой VM (вложенная виртуализация на одном из узлов или
libvirt на ПК — с разрешения пользователя).

## 1e. Обследование и обзор

- Discovery: Proxmox API (узлы, хранилища, гости, IP), скан подсети, отпечатки сервисов.
- Экран «Системы»: карточки узлов/серверов — CPU (модель, потоки, загрузка), RAM,
  хранилища (занято/всего), гости (запущено/всего).
- Экран «Карта сети»: граф (роутер → узлы → гости → сервисы), цвет по статусу.
  Библиотека — @xyflow/svelte (Svelte Flow), раскладка автоматически (dagre/elk).
- Экран «Сервисы»: найденные сервисы с типом, адресом, DNS-именами.

Критерий: на текущей сети Hestia находит то же, что ручной аудит (../../../../README.md,
hosts.csv, proxmox.md): 3 узла, 46 гостей, ключевые сервисы, AdGuard на 10.10.10.15.

## 1f. AdGuard → `hestia.home`

- Отпечаток: HTTP `GET /control/status` (ответ 401/200 с JSON AdGuard), заголовки/страница
  входа AdGuard Home; проверить также DNS на :53 этого хоста.
- Если найден: предложение «Прописать Hestia в AdGuard как `hestia.home`?» — домен редактируется,
  по умолчанию `hestia.<зона>`, где зона определяется по существующим rewrite (у нас `*.home`).
- Доступ: логин/пароль администратора AdGuard (хранится как секрет — понадобится плагину DNS).
- Действие: `GET /control/rewrite/list` → нет конфликта → `POST /control/rewrite/add`
  `{domain, answer: <IP контроллера>}`; если имя занято — показать, кому принадлежит, и спросить.
- Проверка: DNS-запрос к AdGuard → IP контроллера; `http://hestia.home/api/v1/health` с ПК.
- Итог: кнопка «Открыть в браузере» `http://hestia.home`. Сертификат — позже (плагин CA).

## Вне этапа 1

Плагины (DNS, CA, proxy, Samba...), HTTPS, агент на ПК, Windows/Android-клиенты, изменение
существующих сервисов (кроме rewrite в AdGuard по подтверждению).
